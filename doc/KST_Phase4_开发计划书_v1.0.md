# KST Phase 4 开发计划书（严格实施版）

**版本**: v1.0  
**日期**: 2026-11-26  
**前置条件**: Phase 3 已验收通过  
**目标**: 在现有工程级轨道预报、姿态、链路与数据接入基础上，补齐星座设计、高级通信/雷达分析、专业报告体系与自动化接口，使 KST 从“工程分析工具”提升到“可支撑任务设计与系统级分析”的水平。  
**强制原则**：  
- 不得因新增功能降低 Phase 1–3 已达成的视觉标准、计算准确性与架构约束。  
- 所有“必须”项未完成不得宣称 Phase 4 完成。  
- 优先复用或参考成熟开源实现与既有模块，禁止无理由从零重写核心算法。  
- 对推荐开源项目必须进行评估并记录结论。

---

## 1. Phase 4 总体目标

Phase 4 结束后，用户应能够：

- 进行基础星座设计（Walker、街道式等）并快速评估覆盖与 Access
- 开展更完整的通信链路分析（含天线方向图、简单干扰）
- 进行基础雷达探测分析
- 生成结构化、可导出的专业分析报告（含图表）
- 通过脚本/API 自动化完成常见分析流程
- 在三维中清晰展示星座、链路与雷达覆盖

## 3. 详细功能要求（必须严格执行）

### 3.1 星座设计工具（P0）

**要求**：
- 支持至少两种经典构型：
  - Walker Delta / Walker Star
  - 街道式（Streets of Coverage）
- 用户可配置轨道高度、倾角、卫星数量、平面数等参数。
- 一键生成多颗卫星对象并加入当前场景。
- 生成后可直接调用现有传播与 Access 能力。

**禁止**：
- 禁止只生成轨道参数而不实际创建可计算的卫星对象。

### 3.2 星座覆盖与 Access 批量分析（P0）

**要求**：
- 对星座内全部卫星批量计算对指定区域或地面站的覆盖 / Access。
- 输出星座级统计：总覆盖率、平均重访时间、最大间隙等。
- 支持与单星结果对比。
- 计算必须走异步任务。

### 3.3 高级链路预算（P0）

**要求**：
- 在 Phase 3 基础上增加：
  - 简单天线方向图（至少支持全向与余弦型）
  - 可配置大气衰减模型
  - 链路余量随时间变化曲线
- 结果可关联到具体 Access 窗口。
- 支持导出链路预算表格。

### 3.4 基础雷达分析（P0）

**要求**：
- 实现基础雷达方程计算。
- 支持配置发射功率、天线增益、目标 RCS、系统损耗等。
- 输出最大探测距离、信噪比等关键指标。
- 可与 Access 或覆盖结果关联展示。

### 3.5 专业报告生成（P0）

**要求**：
- 支持一键生成分析报告，内容至少包含：
  - 场景与对象摘要
  - 轨道 / Access / 覆盖 / 链路关键统计
  - 简单图表（时间线、余量曲线、覆盖热力等）
- 支持导出为 Markdown 与 HTML（PDF 为加分项）。
- 报告生成过程可调用 AI 进行文字润色（可选，但需可关闭）。

### 3.6 脚本 / API 自动化接口（P1）

**要求**：
- 提供稳定的 REST API，支持：
  - 创建场景与对象
  - 触发传播、Access、覆盖、链路计算
  - 获取结果与导出报告
- API 需有鉴权与基本限流。
- 提供至少一份示例脚本（Python 或 curl）演示完整分析流程。

### 3.7 可视化增强（P1）

- 星座轨道以不同颜色或样式区分平面。
- 链路状态（余量）以颜色渐变或线宽清晰展示。
- 雷达波束或探测范围可在三维中可视化。
- 整体风格继续保持与现有深色 Cesium 场景一致。

## 4. 推荐开源项目与数据源（强制评估）

以下项目在 Phase 4 中必须进行评估，并在设计或实现说明中记录采用/不采用的理由：

| 类别 | 项目 / 来源 | 用途建议 | 优先级 |
|------|-------------|----------|--------|
| **星座设计** | 公开 Walker 构型算法与文献 | 构型生成参考 | 高 |
| **通信分析** | 开源链路预算示例或教材实现 | 链路模型参考 | 高 |
| **雷达** | 基础雷达方程开源实现 | 雷达计算参考 | 中 |
| **报告** | 现有前端图表库（ECharts 等） | 报告图表 | 高 |
| **自动化** | 现有 Axum 路由扩展 | API 设计 | 高 |
| **可视化** | Cesium 官方示例与 `cesium-sensors` | 波束与星座显示 | 中 |
| **数据交换** | CZML 规范 | 场景导出评估 | 低 |

## 5. 技术与架构约束

1. **计算位置**：星座生成后的传播、覆盖、链路、雷达计算必须在 Rust 后端完成。
2. **性能**：
   - 星座批量分析必须走异步任务。
   - 对卫星数量与时间范围设置合理上限并给出提示。
3. **数据模型**：
   - 新增星座配置对象或在场景中支持批量卫星生成记录。
   - 链路与雷达参数扩展到对象模型中。
4. **报告**：
   - 报告生成优先在后端完成结构化数据，前端负责渲染与导出。
5. **视觉一致性**：新增三维元素必须与现有风格协调。

## 6. 开发顺序（强制建议）

1. 数据模型扩展（星座配置、链路/雷达参数）
2. 星座构型生成器
3. 星座批量覆盖与 Access 分析
4. 高级链路预算（方向图 + 余量曲线）
5. 基础雷达分析
6. 三维可视化增强（星座、链路、雷达）
7. 专业报告生成
8. 自动化 API 与示例脚本
9. 开源评估文档与整体联调

## 7. 验收标准（全部满足方可通过）

- [ ] 可生成 Walker 与街道式星座，并加入场景进行计算。
- [ ] 可对星座进行批量覆盖 / Access 分析并输出统计。
- [ ] 链路预算支持天线方向图与余量曲线。
- [ ] 可进行基础雷达方程计算并输出探测距离。
- [ ] 可生成包含图表的分析报告并导出。
- [ ] 提供可用的自动化 API 与至少一份示例脚本。
- [ ] 星座、链路、雷达在三维中有清晰可视化。
- [ ] 所有核心计算在 Rust 后端完成。
- [ ] 批量分析走异步任务。
- [ ] 对推荐开源项目有评估记录。
- [ ] 视觉风格无明显退化。
- [ ] Phase 1–3 已有功能无回退。

---

## 8. 明确禁止事项

- 禁止星座生成后无法直接参与现有传播与 Access 计算。
- 禁止链路或雷达计算放在前端。
- 禁止只做静态报告而无图表或统计数据。
- 禁止自动化接口无鉴权。
- 禁止因星座批量计算导致服务无保护地长时间阻塞。
- 禁止对高优先级推荐项目完全不评估就自行实现。
- 禁止擅自缩减“必须”项后声称 Phase 4 完成。
